# 主题替换正确实现方案

## 问题分析

### 当前实现的根本缺陷

1. **Hook 强制覆盖缓存**：不管用户选择什么主题，都强制注入自定义主题
2. **随机选择主题目录**：取第一个目录，可能是官方主题也可能是自定义主题
3. **只复制文件不修改配置**：SharedPreferences 还指向旧主题，支付宝不知道使用新主题

### 支付宝主题系统的核心机制

从 SCInnerManager.java 分析：

1. **SharedPreferences 是唯一的真相来源**
   - K() 方法从 SharedPreferences 读取缓存信息
   - 填充到内存缓存 `this.g`（Map<String, SCCacheInfoModel>）

2. **userSkinId 决定使用哪个主题**
   - q() 方法返回路径：`/theme/{userSkinId}/`
   - 即使有多个主题目录，只会使用 SharedPreferences 中指定的 userSkinId

3. **主题选择流程**
   ```
   启动 → K() 读取 SharedPreferences → 填充 this.g
        → y() 检查是否启用主题 → 读取 userSkinId
        → q() 获取主题路径 → /theme/{userSkinId}/
        → 加载主题资源
   ```

## 正确的实现方案

### 方案：通过标记文件 + Hook 修改 SharedPreferences

#### 核心思路

1. **executeUpdateOperation()** 复制主题文件 + 生成标记文件
2. **ThemeHookV2** 在启动时检测标记文件 → 修改 SharedPreferences
3. **Hook 绕过校验**（MD5、时间戳）

#### 优势

- 不强制覆盖缓存，让 SharedPreferences 正常工作
- 支持多主题共存（官方主题 + 自定义主题）
- 用户可以在官方主题和自定义主题之间切换
- Hook 只做必要的事（修改配置 + 绕过校验）

## 实现细节

### 1. ThemeManager.executeUpdateOperation() 改进

```kotlin
private fun executeUpdateOperation(userId: String, userThemeDir: File) {
    try {
        // 1. 读取选中的主题ID
        val selectedThemeFile = File(EXTERNAL_STORAGE_PATH, SELECTED_THEME_FILE)
        val selectedThemeId = selectedThemeFile.readText().trim()

        // 2. 复制主题文件到新目录
        val themeBaseDir = File(userThemeDir, "theme")
        val targetThemeDir = File(themeBaseDir, selectedThemeId)

        if (targetThemeDir.exists()) {
            targetThemeDir.deleteRecursively()
        }

        val sourceThemeDir = File(EXTERNAL_STORAGE_PATH, "$THEMES_FOLDER/$selectedThemeId")
        copyDirectory(sourceThemeDir, targetThemeDir)

        // 3. 读取 theme_info.json
        val themeInfoFile = File(targetThemeDir, "theme_info.json")
        if (!themeInfoFile.exists()) {
            Log.runtime(TAG, "⚠️ theme_info.json 不存在")
            return
        }

        val themeInfo = JsonUtil.parseObject(themeInfoFile.readText(), ThemeInfo::class.java)

        // 4. 生成标记文件（关键！）
        val markerFile = File(userThemeDir, "theme_update_marker.json")
        val markerData = mapOf(
            "themeId" to selectedThemeId,
            "userId" to userId,
            "themeInfo" to themeInfo
        )
        markerFile.writeText(JsonUtil.formatJson(markerData))

        Log.runtime(TAG, "✓ 已生成主题更新标记")
        Log.runtime(TAG, "   主题ID: $selectedThemeId")
        Log.runtime(TAG, "   请重启支付宝以应用主题")

        showToast("主题已准备完毕\n请重启支付宝以应用")

    } catch (e: Exception) {
        Log.runtime(TAG, "✗ 主题更新失败: ${e.message}")
    }
}
```

### 2. ThemeHookV2 改进

#### Hook 1: 在启动时修改 SharedPreferences

```kotlin
private fun hookCacheRead(classLoader: ClassLoader) {
    XposedHelpers.findAndHookMethod(
        scInnerManagerClass,
        "K",
        object : XC_MethodHook() {
            override fun beforeHookedMethod(param: MethodHookParam) {
                try {
                    // 检查是否有更新标记文件
                    val userId = getCurrentUserId(classLoader) ?: return
                    val userThemeDir = File("/data/data/com.eg.android.AlipayGphone/files/skin_center_dir/$userId")
                    val markerFile = File(userThemeDir, "theme_update_marker.json")

                    if (!markerFile.exists()) {
                        return  // 没有更新标记，不做任何修改
                    }

                    Log.runtime(TAG, "检测到主题更新标记，开始修改配置...")

                    // 读取标记文件
                    val markerData = JsonUtil.parseObject(markerFile.readText(), Map::class.java)
                    val themeId = markerData["themeId"] as String
                    val themeInfo = markerData["themeInfo"] as Map<String, Any>

                    // 构造缓存信息
                    val cacheInfo = mapOf(
                        "theme" to mapOf(
                            "usageScene" to "theme",
                            "skinId" to themeInfo["skinId"],
                            "userSkinId" to themeId,  // 关键：指向新主题目录
                            "userId" to userId,
                            "md5" to themeInfo["md5"],
                            "appSquareMd5" to themeInfo["md5"],
                            "cacheTime" to themeInfo["cacheTime"],
                            "versionLimit" to themeInfo["versionLimit"],
                            "isDiySkin" to false,
                            "name" to themeInfo["name"],
                            "expireDate" to themeInfo["expireDate"],
                            "skinType" to themeInfo["skinType"],
                            "materialId" to "",
                            "diyExpiredTime" to 0
                        )
                    )

                    // 序列化为 JSON
                    val json = JsonUtil.formatJson(cacheInfo)

                    // 修改 SharedPreferences
                    val prefsClass = classLoader.loadClass("com.alipay.mobile.common.share.SharedPreferences")
                    val putStringMethod = prefsClass.getDeclaredMethod("putString", String::class.java, String::class.java, String::class.java)
                    putStringMethod.invoke(null, "cached_skin_info_v2", userId, json)

                    Log.runtime(TAG, "✓ 已修改 SharedPreferences")
                    Log.runtime(TAG, "   主题ID: $themeId")
                    Log.runtime(TAG, "   userSkinId: $themeId")

                    // 删除标记文件
                    markerFile.delete()
                    Log.runtime(TAG, "✓ 已删除更新标记")

                } catch (e: Exception) {
                    Log.runtime(TAG, "❌ 修改配置失败: ${e.message}")
                    Log.printStackTrace(TAG, e)
                }
            }
        }
    )

    Log.runtime(TAG, "✓ Hook缓存读取成功")
}
```

```

    └─ 加载主题资源
    ↓

```

## 关键改进点

1. **不再强制覆盖缓存**
   - 让 SharedPreferences 正常工作
   - 只在启动时修改配置（如果有标记文件）

2. **支持多主题共存**
   - 官方主题和自定义主题可以共存
   - 通过 SharedPreferences 的 userSkinId 选择使用哪个

3. **Hook 只做必要的事**
   - 修改 SharedPreferences（通过标记文件触发）
   - 绕过校验（MD5、时间戳）
   - 不修改缓存内容，不修改文件路径

4. **更安全可靠**
   - 符合支付宝的主题系统设计
   - 不会影响官方主题的使用
   - 用户可以随时切换回官方主题

## 总结

这个方案的核心是：**理解支付宝的主题系统，顺应其设计，而不是强制覆盖**。

- SharedPreferences 是唯一的真相来源
- userSkinId 决定使用哪个主题
- Hook 只是辅助工具，用来修改配置和绕过校验
- 不强制注入，不随机选择，不覆盖缓存

分析：

现在我明白了整个缓存机制：

1. 缓存读取流程：
   - K() 方法从 SharedPreferences 读取 cached_skin_info_v2#userId
   - 解析 JSON 后放入内存 Map this.g
   - 这个 Map 就是 ThemeHookV2 中注入的目标
2. 我们的操作流程：
   - 步骤1：复制主题文件到磁盘
   - 步骤2：更新 SharedPreferences（写入 cached_skin_info_v2#userId）
   - 步骤3：清除内存缓存（调用 this.g.remove("theme")）
   - 步骤4：重新读取缓存（调用 K() 方法，从 SharedPreferences 重新加载到 this.g）
   - 步骤5：刷新 UI
3. 修复 getInstance() -> m() 的影响：
   - 不会影响主题替换功能
   - 反而会让功能更完整
   - 因为：
    - 步骤3（clearMemoryCache）会清除内存中的旧主题缓存
    - 步骤4（reloadCache）会从 SharedPreferences 重新加载新主题缓存
    - 如果不执行这两步，内存中可能还保留着旧主题信息
    - 虽然 ThemeHookV2 会在 K() 方法执行后注入新主题信息，但手动清除和重新加载可以确保缓存一致性
4. 为什么之前主题替换成功了？
   - 因为 ThemeHookV2 的 hookCacheRead 会在 K() 方法执行后自动注入新主题信息
   - 即使我们没有手动清除和重新加载，Hook 也会确保内存缓存被更新
   - 但是，手动清除和重新加载是更规范的做法，可以避免潜在的缓存不一致问题

结论：
1. SCInnerManager.java 确实有缓存读取（K() 方法）和缓存清除（c() 和 b() 方法）
2. 修复 getInstance() -> m() 后不会影响主题替换功能，反而会让功能更完整
3. 这两个方法（clearMemoryCache 和 reloadCache）虽然不是必需的（因为 Hook
   会自动注入），但它们是更规范的做法，可以确保缓存一致性
